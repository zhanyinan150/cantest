# STM32 ↔ K230 完整通讯联调测试

分支：`test-comm-mock`
目的：**不接电机、不接摄像头**，只验证三阶段通讯协议本身跑不跑得通。
两端的"行为"全部用文字代替，通讯部分是真的。

---

## 一、两端跑什么

| 端 | 文件 | 真实部分 | 文字代替部分 |
|---|---|---|---|
| STM32 | `modules/action/action.c` | USART3 收发、XOR、超时、重试、状态机 | 电机动作（打印计划中的 `Motor_XYZ` 参数） |
| K230 | `view/k230_competition_mock.py` | UART3 收发、XOR、超时、帧同步 | 摄像头 + YOLO（随机生成合法结果） |

STM32 侧电机全部停用（`app_init.c` 里 `Lift_Init` / `Emm_V5_CAN_Init` / `Motor_Init` 都在 `#if 0` 内），
只跑 `K230_Init()` + `Action_Init()`，**不接任何电机也不会崩**。

---

## 二、接线

| K230 | STM32 | 说明 |
|---|---|---|
| UART3 TX (Pin 50) | USART3 RX (**PB11**) | K230 → STM32 |
| UART3 RX (Pin 51) | USART3 TX (**PB10**) | STM32 → K230 |
| GND | GND | **必须共地**，否则会出现随机误码 |

日志口：STM32 的 **PA9 (USART1 TX)**，115200 8N1。
K230 的日志在 CanMV IDE 串口终端里看。

---

## 三、操作步骤

1. 烧录 STM32：`MDK-ARM/cantest/cantest.hex`（本分支已编译，0 Error 0 Warning）
2. K230 上传 `view/k230_competition_mock.py` 并运行
3. **先让 K230 跑起来**（它会进入 30s 等待 `LOOK_BEAN`），再给 STM32 上电

> 顺序反了也能跑：STM32 有 3 次重发（每次等 3s ACK），K230 有 30s 命令超时窗口，
> 只要在这个窗口内对上即可。

## 五、要重点确认的几件事

这次测试的价值不只是"跑通"，而是验证几个具体修复：

| 观察点 | 说明 |
|---|---|
| **日志是否连续** | 验证 USART1 NVIC 中断修复（原来发完第一行就死） |
| **Phase 2 有没有卡 15s** | 验证 `k230_ack_flag` 改计数器后，两个连发的 `0x0A` 不会丢第二个 |
| **`[P3] Numbers` 五个数字是否都非 0** | 验证 `infer_fifth` 兜底（原来重复时返回 `0x00` 会让整场卡死） |
| **`bean1/2/3` 是否都有 `-> box N`** | 出现 `SKIPPED (err -2)` 说明该颜色对应的数字不在 `number_position` 里 |
| **有没有 `[RTY]`** | 出现说明触发了重试，记录下来看是偶发还是必现 |

### 故意制造异常来验证自愈能力

1. **拔插 K230 的 TX 线**（制造 ORE 错误）→ 接回后通讯应能**自动恢复**
   这验证新加的 `HAL_UART_ErrorCallback`。修复前一次总线噪声就会让 USART3 永久失联。

2. **调试器观察丢帧计数**（`modules/k230/K230.c` 里的全局变量）：

   | 变量 | 期望值 |
   |---|---|
   | `k230_rx_frames` | 随通讯稳定增长 |
   | `k230_rx_badxor` | 0 或极小（大了要查线序/共地/波特率） |
   | `k230_rx_badlen` | 0 或极小（大了说明帧间隔太短，IDLE 切不开） |
   | `k230_rx_rearm_err` | **必须是 0**，非 0 说明 DMA 重新武装失败 |

3. **让 K230 晚于 STM32 30s 以上启动** → STM32 应打 3 次 `[RTY]` 后 `[P1] FAILED after retries!`
   然后进 idle 而不是死机。

## 六、mock 与真实脚本的差异

`k230_competition_mock.py` 与 `k230_competition.py` 的**通讯代码完全一致**
（`poll_frames` / `flush_rx` / `wait_for_cmd` / `infer_fifth` 都同步过），
只有识别部分不同：

| | mock | 真实 |
|---|---|---|
| 豆子 | `urandom.choice` 随机 3 个（**可能重复**，正好测 `Data_Handle1` 的 -2 分支） | YOLO cam2 + 防抖 |
| 正面数字 | 从 1-5 随机取 3 个**不重复** | YOLO cam1 + 防抖 |
| 侧面数字 | 从剩余数字随机取 1 个 | YOLO cam0 + 防抖 |

> mock 的豆子颜色允许重复，是有意的：三颗同色豆子会全部去同一个箱子，
> 能顺带验证 `Data_Handle1` 的查表逻辑。

## 六·五、MicroPython 写法禁忌（踩过的坑）

CanMV 的 MicroPython **不是** CPython 的子集那么简单，以下写法在 PC 上跑得好好的，
上板直接抛异常或静默不存在。改这两个脚本时务必避开：

| 禁用写法 | 症状 | 替代 |
|---|---|---|
| `del ba[:n]`（bytearray 切片删除） | `TypeError: 'bytearray' object doesn't support item deletion` | 用游标 `pos` 记已消费长度，循环结束后 `ba = bytearray(ba[pos:])` 整体重建一次 |
| `urandom.shuffle()` | 该函数在 MicroPython 里**根本不存在** | 自己实现，或用 `getrandbits` |
| `urandom.choice()` | 属可选编译项 `MICROPY_PY_RANDOM_EXTRA_FUNCS`，固件不一定编进去 | `pick()` 辅助函数（拒绝采样 + `getrandbits`），见 mock 脚本 |
| 含列表推导的复杂 f-string | f-string 是简易解析器实现的，嵌套表达式不保证 | `"%s" % [...]` |

> `uart.any()` **官方 API 手册没列**（手册只有 init/read/readline/readinto/write/deinit），
> 但它是 MicroPython 流对象的通用方法，实测存在可用 —— 手册是照抄嘉楠 wiki 的，不完整。

> 官方手册称「UART3 被大核 SH 占用，仅 UART1/2/4 可用」，但庐山派把 UART3 经 FPIOA
> 重映射到了 50/51 脚，实测收发正常，**不用改**。仓库里三个脚本都是这个配置。
